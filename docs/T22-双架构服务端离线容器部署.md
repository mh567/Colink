# T22 双架构服务端离线容器部署

对应 [Issue #23](https://github.com/mh567/Colink/issues/23) 和[父规格 #1](https://github.com/mh567/Colink/issues/1)（用户故事 68、70、72）。

## 构建与导出

交付 Linux x86_64（`linux/amd64`）和 ARM64（`linux/arm64`）两份 `lite` 镜像。构建机需要能获取基础镜像及锁定依赖，并能构建目标平台。部署机需要 Docker Engine 和 Compose v2；离线包不包含 Docker。

两个架构使用同一源码和 `uv.lock`。构建阶段使用 `node:20-slim`，运行阶段使用 `python:3.12-slim`。当前锁定的关键依赖为 `colink-harness 1.0.7.post1`、`colink-memory 1.0.3.post1`、`octop-gateway 1.0.3`、`octop-browser 1.0.0` 和 `cryptography 49.0.0`。这些是构建输入，实际镜像 ID 和版本以验收记录为准。

在干净的候选源码仓库根目录执行：

```bash
set -euo pipefail
version=$(sed -n 's/^version = "\(.*\)"$/\1/p' pyproject.toml)
test -n "$version"
git rev-parse HEAD

for arch in amd64 arm64; do
  image="octop:${version}-lite-${arch}"
  docker buildx build --platform "linux/$arch" --load \
    -f docker/Dockerfile --build-arg OCTOP_IMAGE_VARIANT=lite -t "$image" .
  test "$(docker image inspect --format '{{.Os}}/{{.Architecture}}' "$image")" = "linux/$arch"
  docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}}' "$image"
  docker save "$image" | gzip > "octop-server-${version}-${arch}.tar.gz"
done
```

把对应归档和 `docker/docker-compose.offline.yml` 一起交付。`lite` 不预装中央浏览器和远程桌面；办公文件及网页任务由正式桌面客户端在员工设备上执行。

## 离线导入与首次配置

部署机阻断公网，保留到员工客户端和内网模型的连接。以下示例为 ARM64，x86_64 将 `arch` 改为 `amd64`；`version` 使用收到的包版本。执行 `up` 前必须核对镜像架构与 Docker 宿主机一致。

```bash
set -euo pipefail
arch=arm64
version=1.0.3b3
export OCTOP_IMAGE="octop:${version}-lite-${arch}"
docker load -i "octop-server-${version}-${arch}.tar.gz"
test "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" = "linux/$arch"
test "$(docker image inspect --format '{{.Os}}/{{.Architecture}}' "$OCTOP_IMAGE")" = "linux/$arch"
docker compose -f docker/docker-compose.offline.yml up --wait
curl -fsS http://localhost:8088/api/health
```

- `pull_policy: never` 禁止 Compose 从仓库拉取镜像。离线编排关闭公网专家和插件市场，应用的其他网络访问仍由部署网络限制。用旧数据卷迁移时，检查卷内 `env` 和已启用的外部渠道，避免沿用指向公网的配置。
- 数据默认写入宿主机 `~/.octop`，可用 `OCTOP_DATA` 指定持久目录。打开控制台读取设置向导提示，用数据目录内 `octop-login.txt` 的口令解锁，绑定数据库，创建管理员并配置内网模型。首次绑定前 `/api/health` 的 `db` 为 `false`，完成后应为 `true`。
- 新卷未缓存 `general-assistant` 时不会自动创建该专家。用户需要专家时，在专家页点击「新建专家」，使用内置「通用专家」（`default`）模板。
- 离线编排默认限制 4 核 CPU、4 GiB 内存、65535 个文件描述符、1 GiB 共享内存。CPU 和内存可用 `OCTOP_CPUS_LIMIT`、`OCTOP_MEM_LIMIT` 调整。既有在线编排沿用原设置。
- ARM64 入口在 CPU 只报告 `sve2`、不报告 `sve` 且未手动设置 `OPENSSL_armcap` 时禁用 OpenSSL 的 ARM 指令探测。麒麟实机兼容性仍须现场验证。

## 验收步骤与状态

在两种目标架构分别使用干净的 Docker 环境、空数据目录和同一候选版本。记录源码提交、实际镜像 ID、部署机系统与架构、Docker/Compose 版本、桌面客户端版本和每步结果：

1. 阻断公网后导入镜像，按上述命令启动，核对 `/api/health` 的 `ok`、`version`、`arch`。用 `docker inspect` 确认容器实际使用的镜像 ID、CPU、内存、共享内存和 `nofile` 限制；确认未启用特权模式、未挂载 Docker 套接字。
2. 用设置向导绑定数据库并创建管理员，配置和试用内网模型。创建员工，启动正式客户端完成设备接入和审批。
3. 在员工设备实际生成并打开 DOCX、XLSX，在本机浏览器完成一次内网任务。核对本机产物、服务端审计和未授权时的拒绝结果；也应确认服务端没有启动无关外部聊天服务。
4. 保留同一个 `OCTOP_DATA`，执行 `docker compose -f docker/docker-compose.offline.yml up --wait --force-recreate`。确认健康检查恢复、账号仍可登录、模型配置与审计保留，设备无需重新审批。
