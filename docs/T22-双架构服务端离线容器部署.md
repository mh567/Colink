# T22 双架构服务端离线容器部署

核验日期：2026-11-20。对应 [Issue #23](https://github.com/mh567/Colink/issues/23) 及[父规格 #1](https://github.com/mh567/Colink/issues/1)（用户故事 68、70、72）。

本记录规范 Linux x86_64 与 ARM64 双架构服务端容器镜像的离线构建、导出、导入与编排运行，记录两套架构在无外部网络环境下的首次配置、客户端设备接入、本机任务授权、持久化数据保持及反向安全边界验证结果。

## 2. 容器适配处理与资源限制规范

### ARM64 SVE2 OpenSSL 指令集兼容处理

在银河麒麟 V10 SP1 或虚拟化 ARM64 环境下，宿主内核（如 Linux 5.4）在 `/proc/cpuinfo` 中广播 `sve2` 特征但缺少 `sve` 基础特征。静态链接 OpenSSL 的 `cryptography` 在初始化 `OPENSSL_cpuid_setup` 时因执行 `cntb x0` 会遭遇致命 `SIGILL`（退出码 132）。

在容器化环境中，通过两层兜底保护确保 ARM64 容器稳定启动：
1. **容器入口脚本防护**：在 `docker/docker-entrypoint.sh` 的 `octop_prepare_arm_runtime` 增加 CPU 特征探测。当架构为 ARM64，且 `/proc/cpuinfo` 出现 `sve2` 但缺少 `sve`、且未显式指定 `OPENSSL_armcap` 时，自动注入 `export OPENSSL_armcap=0` 并打印诊断日志。
2. **应用初始化防护**：`octop` Python 包初始化阶段（`octop.infra.utils.arm64_compat`）再次校验并锁定环境变量，确保任何独立命令行进程均不发生 OpenSSL SVE2 崩溃。

### 架构与版本探针查询能力

为满足容器“应用版本和架构结果可查”的验收要求：
- 健康检查端点 `GET /api/health` 免鉴权返回当前版本 `version`、系统架构 `arch`、数据库绑定状态 `db` 及运行总览。
- 容器入口脚本启动时输出包含架构信息的日志：`正在启动 Octop (架构: $(uname -m))`。

### 显式资源限制与隔离要求

为避免多智能体任务消耗过多宿主机资源或发生文件描述符耗尽，编排文件严格定义了资源上限与边界：
- **CPU 限制**：默认上限 4.0 核（可通过 `COLINK_CPUS_LIMIT` 调整）。
- **内存限制**：默认上限 4096MB（可通过 `COLINK_MEM_LIMIT` 调整）。
- **文件描述符**：`nofile` soft 与 hard 限制均设为 `65535`。
- **共享内存**：`shm_size` 设为 `1gb`。
- **安全与职责边界**：
  - 编排文件**禁止**挂载宿主机 `/var/run/docker.sock`，**禁止**开启 `privileged: true`。
  - **不运行**外部 IM 聊天服务（无飞牛/企业微信/飞书/钉钉/QQ/Discord 外部渠道配置与网关轮询）。
  - **不以中央浏览器或服务器任意命令执行替代客户端能力**，所有文件任务（DOCX/XLSX）与网页业务操作均在员工接入的本人设备上执行，服务端只负责设备握手、鉴权转发与审计留痕。

## 3. 离线镜像导入与编排规范

### 1. 离线镜像打包与导出规范

在具备构建环境的机器上按架构分别构建并导出压缩包。可通过 `OCTOP_IMAGE_VARIANT` 选择轻量纯服务端（`lite`）或包含浏览器调试运行时的完整版（`full`）：
- `OCTOP_IMAGE_VARIANT=lite`：轻量纯服务端部署（推荐），不安装中央 Chromium 与 Xvnc，体积大幅缩减，契合“办公与网页任务完全由客户端本机执行”的架构约束。
- `OCTOP_IMAGE_VARIANT=full`：包含中央 Chromium 与 Xvnc 调试环境。

```bash
# 构建并导出 x86_64 纯服务端离线镜像
docker build -f docker/Dockerfile --build-arg OCTOP_IMAGE_VARIANT=lite -t octop:1.0.3b3-amd64 .
docker tag octop:1.0.3b3-amd64 octop:latest
docker save octop:latest | gzip > octop-server-amd64.tar.gz

# 构建并导出 ARM64 纯服务端离线镜像（在 ARM64 构建机或通过 buildx）
docker build -f docker/Dockerfile --build-arg OCTOP_IMAGE_VARIANT=lite -t octop:1.0.3b3-arm64 .
docker tag octop:1.0.3b3-arm64 octop:latest
docker save octop:latest | gzip > octop-server-arm64.tar.gz
```

### 2. 目标机离线导入与编排启动

将导出的压缩包与编排文件传输至目标离线内网主机后，断开任何公网连接执行：

```bash
# 导入镜像（两架构命令一致，不从互联网拉取任何镜像层）
docker load -i octop-server-<arch>.tar.gz

# 检查已导入镜像
docker images octop:latest

# 使用专用离线编排文件启动服务（默认 pull_policy: never，不尝试连接外网仓库）
docker compose -f docker/docker-compose.offline.yml up -d
```

## 6. 后续物理机实测建议

1. 将正式发布的双架构离线镜像（`octop-server-amd64.tar.gz` 与 `octop-server-arm64.tar.gz`）分发至目标干净物理机（x86_64 服务器与银河麒麟 ARM64 裸机）。
2. 在完全拔掉网线的断网状态下，执行 `docker load -i octop-server-<arch>.tar.gz` 与 `docker compose -f docker/docker-compose.offline.yml up -d`。
3. 执行 `curl http://localhost:8088/api/health`，核实返回的 `version` 与 `arch` 字段与目标机实际硬件相符。
4. 在办公测试网段内使用正式桌面客户端接入，验证首次审批、DOCX/XLSX 办公文档流转及服务重启后数据保持。
