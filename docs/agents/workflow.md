# Colink 开发工作流

本文件承接 [AGENTS.md](../../AGENTS.md)，沿用 cheese-internal 的开工检查、任务边界、验证和审查模式。规则适用于人工与编码智能体；执行权限仍以用户明确授权为准。

## 仓库与事实来源

- 本仓库为 `mh567/Colink`，日常任务以最新 `origin/main` 为基线。默认在 `codex/<任务描述>` 分支开发，日常合并请求以 `main` 为目标；用户明确指定继续当前分支时按其指令执行。
- 历史 Octop 文档中的 `develop`、`feature/*` 和 `release/*` 流程属于上游发布约定，不能自动当作 Colink 日常开发流程。涉及发布时另行读取实际工作流并确认目标。
- 同一事项只维护一份规格。已有 GitHub 工单时，读取正文、评论、验收标准、标签、负责人和阻塞关系；未授权发布时，在当前对话或用户指定的本地文档交付。
- `docs/architecture.md` 和 `docs/adr/` 记录技术约束；其中 ADR 是 Architecture Decision Record，即架构决策记录。实现与已接受的决策冲突时先说明冲突并确认变更，不静默覆盖。
- 版本、依赖和命令以 `pyproject.toml`、`uv.lock`、`dashboard/package.json`、`Makefile` 及实际脚本为准。文档不能证明功能已经通过实测。

示例：工单已记录模型连接测试需要离线可复现，就沿用该验收条件；不能从旧版介绍中推导出必须调用真实外部模型，也不能把测试通过复制成未经核对的工单完成状态。

## 开工前同步

每次开发会话、切换任务或恢复暂停的工作时，先完成以下步骤；连续的一组本地编辑无需在每个文件前重复拉取。

### 1. 检查现场并刷新远端

```bash
git status --short --branch
git branch -vv
git remote -v
git fetch --all
```

检查是否存在未提交改动或正在进行的合并、变基、拣选提交操作。保留任务开始前已有的改动，先取得其处理方向；不要自行提交、隐藏、丢弃或移动。远端获取必须成功，失败时报告具体阻塞，暂停依赖最新基线的修改。

确认 `origin` 对应本仓库，不擅自添加远端、修改远端地址或把上游同步混入当前任务。

### 2. 检查与最新 main 的差异

```bash
git rev-list --left-right --count HEAD...origin/main
git log --oneline HEAD..origin/main
git diff --name-only HEAD...origin/main
```

第一条输出依次是当前分支独有和远端 `main` 独有的提交数。继续读取涉及本任务文件、接口、数据结构、依赖和构建产物的实际差异；只看数量不算完成检查。

示例：输出 `3 2` 表示双方各有独有提交，不是当前分支只领先三个提交。若远端两个提交涉及本次权限判断，必须先确认影响，再继续实现。

### 3. 确认并同步本次开发分支

向用户说明当前分支、跟踪分支、工作区状态和主线差异，确认继续已有分支或从最新 `main` 开始。已在当前任务确认过的选择持续有效。

新任务在工作区可安全切换且用户确认后执行，最后一行的名称替换为本次实际分支：

```bash
git switch main
git pull --ff-only origin main
git switch -c codex/task-description
```

已有分支具备跟踪分支时，在该分支执行 `git pull --ff-only`。新建且尚未发布、确认以 `origin/main` 为基线的分支可执行 `git pull --ff-only origin main`；不要为通过检查而把 `origin/main` 设为任务分支的跟踪分支。拉取不能快进时保留现场，说明分叉和集成选择。

开始更新前再次确认分支和工作区；同步后重新检查与 `origin/main` 的差异。仅更新本地 `main` 或仅拉取任务分支，均不能证明任务分支包含最新主线。

### 4. 在明确节点集成主线

出现与本任务重叠的修改、较长暂停后的相关变化、合并冲突，或准备创建合并请求、转正式审核、请求最终审核、交付合并时，检查是否需要集成最新 `origin/main`。

集成须在已授权范围内执行；需要生成合并提交但尚未获准提交时，先交付具体集成方案。已发布或共享分支采用合并方式，获得相应授权后可用 `git merge --no-edit origin/main`；未发布的单人分支仅在明确授权后变基。不要强制推送覆盖历史。

集成完成后检查：

```bash
git diff --name-only --diff-filter=U
git merge-base --is-ancestor origin/main HEAD
```

第一条应无输出，第二条应返回 `0`。然后运行受影响检查。未集成且仍有主线差异时，报告其范围和未集成原因，不能宣称基线一致。

## 选型与最小验证

新项目、较大功能或新增基础设施按以下顺序执行，方案确认后再编码：

1. **明确需求。** 简述目标、谁在什么情况下使用、首期必须功能、部署位置、预算和数据隐私限制，区分必须满足和可以妥协的偏好。
2. **寻找现成方案。** 联网查找完整产品，再找通过配置、插件或少量修改可用的产品，最后找模块、模板、集成组件及参考实现。技术栈不同本身不是排除理由。
3. **比较最相关的三个候选。** 附官方仓库和文档，逐项区分开箱即用、需要改造、无法满足；核查维护与发布情况、许可证和商业限制、付费边界、迁移成本、升级负担及公网部署责任。实际使用规模只写可核实证据，不用收藏数或下载量代替用户数。不足三个候选时说明检索范围和原因。
4. **给出明确推荐。** 比较直接采用、基于现有项目改造、复用组件自行开发三条路径，以从现在开始的剩余工作量、长期维护和安全责任为依据。每个候选提供至少一个贴合需求的具体操作示例，最后明确采用、复用和必须自行实现的部分。
5. **验证关键疑点。** 把可能改变结论的兼容性问题写成最小验证：验证什么、输入或操作、通过标准、预计投入、停止条件。获得用户同意后执行，不先建完整系统。明确区分官方声明、实际核查和推测。

控制调研篇幅和投入，先给简洁比较；仅在关键疑点影响决策时继续深入。找不到完全匹配项时写“本次检索未发现合适的完整方案”，继续检查可复用部分。已有代码不是继续自研的充分理由。

示例：假设需求是程序生成草稿、管理员审核后发布，就核查候选能否接收草稿、限制程序账号发布权限，并让管理员完成审核。最小验证可以只提交一篇示例草稿、尝试用程序账号发布并确认被拒绝，再由管理员发布；三项均通过才证明这条流程可用。

## 任务与协作状态

一个任务分支聚焦一个可验收问题；已有工单时关联对应工单和合并请求。需求变化先同步验收标准，不把临时想法顺手加入实现。

已获准在 GitHub 发布规格和任务时，父工单保存整体规格，子工单保存可实施任务；依赖优先用平台的原生阻塞关系，无法使用时在正文写明。前置依赖未解除时可以调查接口和测试边界，不能把依赖不存在的功能标为可交付。

沿用以下状态语义；这些是工作流约定，不表示当前仓库已经创建这些标签。实际创建、修改标签与状态均需授权。

| 标签 | 含义 |
| --- | --- |
| `needs-triage` | 等待评估范围与优先级 |
| `needs-info` | 缺少影响实施的信息 |
| `ready-for-agent` | 规格和验收标准完整，可以实施 |
| `ready-for-human` | 需要人工决策或操作 |
| `wontfix` | 已明确决定不实施 |

示例：前置任务负责新增设备身份字段，当前任务负责撤销设备；字段尚未合入时先确认接口契约和撤销测试场景，不复制一份临时身份存储。涉及共享文件的冲突先在当前对话提出，获准后再同步到关联工单。

## 验证与检查范围

从最能发现本次错误的检查开始。只新增能验证实际契约的测试，复用项目测试辅助设施；数据库测试走生产迁移，使用临时数据库，不手写另一份表结构替代实际迁移。

| 改动范围 | 验证要求 |
| --- | --- |
| 仅 Markdown 文档 | `git diff --check`；检查本地链接与标题锚点、引用文件、命令来源、规则冲突和实际改动范围。当前没有独立文档检查命令，不凭空引用其他项目的脚本 |
| 后端代码 | `make lint`、`make typecheck`，以及 `uv run pytest <受影响测试路径> -q`；完整交付检查使用 `make all` |
| 控制台代码 | 在 `dashboard/` 下执行 `npm run lint`、`npm run format:check`、`npx tsc -b`、`npm test -- <受影响测试路径>`；执行 `make build-frontend` 验证产物生成 |
| 中英文语言包 | 在相应代码检查之外执行 `uv run pytest tests/unit/i18n -q`，检查键、插值和前后端错误码一致性 |
| 对外接口 | 在相应代码检查之外查看 `/api/docs`，核对接口摘要、请求字段、响应结构和鉴权要求 |
| 跨模块或无法限定影响面 | `make all`；涉及前端时补充 `make lint-frontend`、`make typecheck-frontend`、在 `dashboard/` 执行 `npm test` 和前端构建 |

`make all` 会先运行 `format-all`，可能写入后端和前端格式化结果；它不包含前端类型检查、前端测试或前端构建。检查后查看差异，不把无关格式化混入任务。

代码交付默认要求完整后端检查通过；开发中的针对性检查用于快速反馈，不等同于完整检查通过。仅文档更新按文档行验证，不为文档修改安装整套运行依赖或改动源码。需要真实凭据或收费模型的测试先确认本次授权与成本范围。

Linux 和 Windows 的自动检查配置在 `.github/workflows/ci.yml`。本机通过不能代替另一平台结果；界面修改还应提供实际交互结果或截图，不以构建成功证明交互正确。

准备获准的本地提交时，先确认 `git config --get core.hooksPath` 为 `.githooks`；未设置则执行 `make install-hooks`。当前钩子执行 `make precommit` 和控制台构建，`make precommit` 使用受影响测试选择。钩子的文档快速路径目前只匹配 `README.md` 和 `README.*.md`，不覆盖所有 Markdown；不要误称 `AGENTS.md` 提交会自动跳过代码检查，也不要擅自修改或跳过钩子。

失败记录应包含命令、失败摘要、环境和影响范围。无法运行时报告缺少什么以及哪些结论尚未验证，不把未运行、跳过或模拟结果写成通过。

示例：只修改本文件时，验证引用的测试命令确实存在且链接有效即可；修改模型保存逻辑时，则必须验证保存与失败行为，不能以文档检查通过代替代码验证。

## 提交与合并请求

以下动作只在获得相应授权后执行，文档中的示例命令不构成授权。

- 提交前检查 `git diff` 和 `git diff --cached`，按文件暂存本次任务内容，不纳入任务开始前的改动。
- 提交使用约定式提交格式及中文摘要，范围是具体模块。每个提交同时具备密码学签名和 DCO（Developer Certificate of Origin，开发者原创声明）签署，使用 `git commit -S --signoff`。签名身份使用用户已有配置，不代替用户声明未确认的权利。
- 提交后用 `git cat-file commit HEAD` 核对 `gpgsig` 和 `Signed-off-by`；推送后另核对 GitHub 的 `Verified` 状态。本地有签名字段不代表远端验证一定通过。签名环境缺失时先交付改动和提交说明，说明阻塞，不静默降级为未签名提交。
- 日常任务的合并请求目标为 `main`，正文按[仓库模板](../../.github/pull_request_template.md)写明问题、结果、验证、风险和限制；标题与解释使用中文，技术标识保留原样。
- 默认创建草稿，使用 `--draft`。获准创建草稿不等于获准转正式审核、邀请他人审核、合并或关闭工单。
- 关联工单使用明确的引用；只有用户授权合并后关闭且全部验收满足时才使用 `Closes #编号` 等自动关闭关键字。
- 界面变更附实际截图或操作证据；外部网络或权限边界变化提供对应行为证据。敏感数据不进入提交正文和截图。

示例：用户仅授权为模型配置修复创建合并请求，即使所有测试通过，也应创建以 `main` 为目标的草稿，说明验证结果；不能顺带合并或关闭尚有验收缺口的工单。

## 审查与完成报告

沿用规范与需求两个审查维度，并单独列出验证边界。以下英文标题是与参考项目一致的固定审查字段：

- **Standards（规范）**：模块边界、依赖方向、命名、用户提示、数据与权限、测试价值；问题必须有文件位置、依据、影响和建议。
- **Spec（需求）**：逐项对照验收条件，记录缺失、错误实现和范围外内容。
- **Verification and limits（验证与限制）**：列出实际运行的检查、平台、模拟边界、未执行项，以及本次是自查还是独立审查。

没有发现问题时对应项写 `0 项`，但不能把没有运行的检查描述为通过。审查结论和发布、合并权限分开；获准发布审查时再发送评论，不因本文件规定格式而自动发表。

已有远端检查时先核对其提交和结果，不为只读审查运行会格式化工作区的命令。需要本地复现才能判断的问题仍应针对性验证，并说明与远端检查的不同覆盖范围。

完成报告说明结果、验证证据、实际限制，并追加 [AGENTS.md](../../AGENTS.md)要求的中文提交说明。未获准提交和推送时，保留可检查的本地改动。

示例：测试覆盖模拟模型响应，但没有真实模型凭据，就写“模拟成功和失败响应的测试通过，真实模型连接未验证”，不能写“模型接入全部验收通过”。

## 发布与异常处理

发布是独立授权范围。执行前阅读实际 `.github/workflows/`、`.cursor/skills/publish/SKILL.md` 和本次平台脚本，确认标签、目标仓库、构建产物、触发的外部操作及验收范围，不自动套用上游 `develop` 发布步骤。

冲突、权限不足、依赖安装失败或任务范围发生变化时，保留现场，说明具体问题和可选处理；可以继续不受阻塞的调查与验证，不用重置、删除数据、关闭检查或改写历史掩盖问题。

示例：麒麟发行候选能解压但启动失败，结果应记录为启动未通过；其他平台测试通过不能替代这项验收，也不能据此发布该候选。
